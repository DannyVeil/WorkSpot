# WorkSpot

Полноценное веб-приложение для бронирования мест в коворкинге: React-фронтенд,
REST API на Node.js/Express, MongoDB и Redis для защиты от двойных броней.

## Что внутри

```
WorkSpot/
├── client/          # React 19 + Vite + Tailwind CSS 4
├── server/          # Express 5 + MongoDB (Mongoose) + Redis
└── workspot.tsx     # исходный дизайн-макет (сохранён как референс)
```

- **Frontend** — `/client`, инструкция в [`client/README.md`](client/README.md).
- **Backend** — `/server`, API и схема данных в [`server/README.md`](server/README.md).
- **Дизайн** — `workspot.tsx` не изменялся; его вёрстка разложена по компонентам
  и страницам в `client/src`.

## Быстрый старт

```bash
# 1. Базы данных (в этой системе — user-сервисы)
systemctl --user start mongodb redis

# 2. Бэкенд
cd server
npm install
cp .env.example .env          # при необходимости
npm run seed                  # каталог мест + демо-аккаунт + демо-брони
npm run dev                   # http://localhost:4000

# 3. Фронтенд (в новом терминале)
cd client
npm install
npm run dev                   # http://localhost:5173
```

## Как защищены брони

Оформление разбито на два шага:

1. `POST /api/bookings/hold` — Redis атомарно (`SET NX PX`) закрепляет слоты
   на 10 минут. Другие пользователи сразу видят их занятыми.
2. `POST /api/bookings` — после подтверждения создаётся бронь в MongoDB.

Дополнительно работают распределённый мьютекс Redis и уникальный multikey-индекс
MongoDB `{ space, slots }`, поэтому один и тот же слот нельзя забронировать дважды
даже при одновременных запросах.

Подробности — в `server/README.md`.

## Чат поддержки через Telegram

Чат в личном кабинете связан с Telegram-ботом `@My_message_portfolio_bot`:

1. Пользователь пишет сообщение на сайте (`POST /api/support/messages`).
2. Бот пересылает его оператору (`TELEGRAM_ADMIN_CHAT_ID`) с именем, email,
   id пользователя, временем и текстом.
3. Оператор нажимает **Reply** на это сообщение и отвечает — ответ сохраняется
   и появляется в чате на сайте у нужного пользователя (опрос каждые 5 секунд).

Пока оператор не ответил, пользователь не может отправить второе сообщение: поле
ввода блокируется с обратным отсчётом. Если ответа нет 5 минут, отправка снова
разрешается; ответ оператора открывает чат сразу. Дубли при параллельных запросах
отсекает Redis-блокировка, а сервер дополнительно отвечает `429 SUPPORT_REPLY_PENDING`.

Сервер сам опрашивает Telegram (`getUpdates`, long polling), поэтому вебхук и
публичный URL не нужны — бот работает даже при локальном запуске. Настройки в
`server/.env`:

```env
TELEGRAM_BOT_TOKEN=…            # токен от @BotFather
TELEGRAM_ADMIN_CHAT_ID=…        # chat id оператора
TELEGRAM_POLLING=1              # 0 — отключить бота
```

Если токен не задан, чат продолжает работать локально: сообщения видны
пользователю, но оператору не уходят.

## Персональный QR-пропуск

В личном кабинете («Мой QR-код») показывается настоящий QR, значение которого —
подписанный ключ с ограниченным сроком действия:

```
WSP1.<userId>.<expiresAt>.<signature>
```

`signature` — HMAC-SHA256 от id пользователя и срока действия, ключ подписи
(`PASS_QR_SECRET`) известен только серверу. Подделать id или продлить срок нельзя:
изменённый токен не пройдёт проверку. По умолчанию ключ живёт 5 минут, клиент
обновляет его каждые 30 секунд, пока блок открыт, и рядом показывается короткий
ключ (`A1B2-C3D4`) для ручного ввода и обратный отсчёт.

```env
PASS_QR_SECRET=…          # пусто — выводится из JWT_SECRET
PASS_QR_TTL_SECONDS=300   # срок жизни одного ключа
```

Смена `PASS_QR_SECRET` мгновенно обнуляет все выданные пропуска, не затрагивая
JWT-сессии пользователей.

## Управление через Telegram

Тот же бот `@My_message_portfolio_bot` принимает админ-команды — только из чата
оператора (`TELEGRAM_ADMIN_CHAT_ID`), остальным он по-прежнему отвечает справкой.
Пользователя можно указать email’ом, полным id или последними 6 символами id,
бронь — кодом вида `BK-123456`.

| Команда | Что делает |
| --- | --- |
| `/users [поиск]` | последние пользователи (по имени или email) |
| `/user <кто>` | карточка: профиль, активные и последние брони |
| `/bookings <кто>` | последние 10 броней |
| `/rename <кто> <имя>` | изменить имя в профиле |
| `/phone <кто> <номер\|->` | изменить или удалить телефон |
| `/qr <кто>` | выдать новый QR-пропуск картинкой + короткий ключ |
| `/extend <BK-123456> <30m\|1h\|90m>` | продлить бронь |
| `/cancel <BK-123456> [причина]` | отменить бронь |
| `/help` | справка по командам |

Продление и отмена идут через те же проверки, что и обычное бронирование:
мьютекс места и даты, пересечение с другими бронями, лимит `MAX_BOOKING_HOURS`,
последний слот до 23:30. Цена пересчитывается по снимку `pricePerHour` брони,
а пользователь получает уведомление в личный кабинет («Бронь продлена»,
«Имя обновлено» и т. д.). `/qr` всегда выпускает свежий подписанный ключ; старый
QR живёт максимум свои 5 минут.

Всё это работает без вебхука — через тот же long polling, что и чат поддержки.

## Публикация через ngrok

`start-tunnel.sh` поднимает всё сразу — MongoDB и Redis, API, Vite — и открывает
доступ из интернета через туннель ngrok:

```bash
ngrok config add-authtoken <токен>   # один раз, токен из dashboard.ngrok.com
./start-tunnel.sh                    # запуск, Ctrl-C — остановить
./start-tunnel.sh --seed             # + пересоздать демо-данные
./start-tunnel.sh --no-tunnel        # только локально, без ngrok
./start-tunnel.sh --stop             # остановить фоновые процессы
```

Скрипт сам подставляет публичный адрес в `CORS_ORIGINS` (`server/.env`), поэтому
после перезапуска туннеля с новым доменом ничего править руками не нужно.
Туннель один — на Vite (`:5173`), а `/api` и `/healthz` проксируются в Express,
так что фронтенд и API живут на одном origin.

Адрес по умолчанию случайный. Чтобы он не менялся, возьмите бесплатный static
domain в панели ngrok и запускайте:

```bash
NGROK_DOMAIN=my-app.ngrok-free.app ./start-tunnel.sh
```

Логи — в `.logs/` (`server.log`, `client.log`, `ngrok.log`). На бесплатном плане
ngrok браузер один раз показывает страницу-заглушку — нужно нажать «OK».

Скрипт держит блокировку `.logs/run.lock`, поэтому второй экземпляр не запустится
поверх первого, а сначала аккуратно остановит предыдущий (иначе новый запуск гасил
только что поднятый туннель). Остановка ngrok адресная — по `.logs/ngrok.pid`,
чужие процессы ngrok не затрагиваются. Если туннель не поднялся, скрипт сам
печатает последние строки `.logs/ngrok.log` — это главный лог ngrok, а
`.logs/ngrok.out` обычно пустой.

Сквозной сценарий (вход → карта → резерв → подтверждение → кабинет → отмена)
проверен через Vite-прокси и headless-браузер.
